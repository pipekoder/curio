# Cultural Intelligence V3 — default-off completion pass

## Assessment and reused boundaries

Latest base is `main` with #68, #69, #71 and #74. V3 reuses the published D1 catalog, exact-version owner facts and Muse visual observations, the Chief Editor → independent Reviewer → bounded Revision → Confirmation flow, the shared `magazine-v1` budget Durable Object, and #71's draft-only long-form source interface. It does not change Silver Field, the public Editorial request schema, the four-unit short-form reservation, or the long-form job lease/state machine.

Draft #70 contributed the allowlisted HTTPS, no-redirect, bounded-text retrieval pattern. V3 adds passage IDs, document fingerprints, a structured Muse research planner, claim-to-passage and relationship contracts, an operator review boundary, private R2 evidence packs, and optional use of reviewed claims as exact-version Editorial sources. #70 is not merged. Meta Muse Spark 1.3 chat completion is the only verified AI capability in this repository. No verified Muse embedding or web-search endpoint exists; retrieval is lexical-only. An embedding provider is **not configured**. No graph database or D1 migration is needed for the bounded pack model.

## Trust and data flow

`POST /api/operator/catalog/cultural/plan` requires existing catalog-operator Bearer authorization, same-origin protection, explicit consent, `CULTURAL_INTELLIGENCE_V3_ENABLED=true`, `CULTURAL_RESEARCH_PLANNER_ENABLED=true`, valid Muse configuration, and a successful **one-unit atomic reservation** in the existing Durable Object before one bounded planner call. No retry is made. A planner question or relationship is a hypothesis, never evidence. This operator preparation call is separate from the existing four-unit public Editorial workflow. The current standard per-IP cooldown applies; operators should not chain calls expecting a cooldown exemption.

`POST /api/operator/catalog/cultural/retrieve` accepts 1–3 operator-selected URLs from `RESEARCH_SOURCE_ORIGINS`. It makes at most three 10-second, 128-KiB HTTPS text requests, rejects redirects and unsafe/unallowlisted URLs, deduplicates by content hash, and returns lexical relevance, a separate source-quality eligibility component, bounded passage offsets, stable IDs, fingerprints, retrieval times, and `pending` verification/rights. It stores a private R2 fingerprint proof for each captured passage, never the full fetched page. It does not search the web for URLs. Tracking query parameters are removed during canonicalization. Token-overlap and exact-phrase rankings are fused using deterministic TypeScript RRF only when both have useful signal and at least two eligible sources exist; otherwise the mode is `lexical_only`. This is **not Hybrid RAG or semantic retrieval**. It does not prove source authority, factual accuracy, ownership, or quotation rights. A cached passage can be stale; operator review must check the original source and freshness before approval. HTML extraction is intentionally basic and unsuitable for complex sites.

`POST /api/operator/catalog/cultural/research` runs one budget-reserved planner call and at most two retrieval rounds over operator-supplied URLs. It may stop, narrow, or return a candidate pack. It never approves evidence automatically. The operator must inspect and edit the candidate's source verification, rights, claims and relationships before `POST /api/operator/catalog/cultural/packs` can approve it. The latter route rechecks current publication, AI-analysis grants and R2 media for every exact asset version, verifies bounded identities and captured passage fingerprints, and stores the approved pack privately in existing R2 with a monotonic review revision and conditional write. `/cultural/packs/revoke` records revocation, and a revoked pack is ineligible on the next read. The operator must verify source authority, claim support, conflicts, quotation rights and image relevance. The code cannot independently prove that a cited passage is true or legally reusable. Use paraphrase-approved evidence; quoted text needs separate rights approval.

`POST /api/operator/catalog/cultural/relationships/candidates` uses one separately reserved Muse call to extract at most eight *unapproved* typed edges from reviewed claims. It detects duplicate and opposing edges. A documented edge requires a reviewed factual claim; a comparison needs a reviewed factual or comparison claim. The operator must resolve conflicts and place approved edges in the evidence pack. `GET /cultural/relationships?versions=...&topic=...` returns only currently eligible, approved, topic-matching edges to the operator. No graph database is required.

With `CULTURAL_INTELLIGENCE_V3_ENABLED=false` (the committed default), Editorial V2.1 is unchanged. When enabled, `/api/editorial` only reads a private, precomputed pack whose exact set of asset-version IDs matches the current publication-filtered pool. It makes **no live web requests and no additional Muse call**. Invalid, absent, stale-version or revoked packs fail closed to the existing V2.1 workflow. Approved cultural claims become `cultural_claim` Editorial sources with same-asset IDs; the Chief Editor, independent Reviewer, Revision Editor and Confirmation review receive the same source set. The normal source-ID validation, publication checks, Reviewer hard-failure behavior, fallback and cache revalidation still apply. Pack content participates in the generation cache key. R2 pack key derivation is stable and private; revocation removes it from the eligible editorial pool, and approval is revalidated at read time.

The private draft-only long-form workflow now uses #71's existing D1 job and 18-call ceiling. Operator `POST /cultural/articles` builds a job from currently eligible D1 owner-supplied mockup facts and, if present, reviewed cultural claims; it accepts no caller-supplied facts. The inherited `verified` source field denotes authorized source identity, **not independent merchant verification**. `POST /cultural/articles/:id/advance` requires explicit consent and `CULTURAL_LONGFORM_ENABLED=true`, rechecks publication, AI grants, exact R2 media, current owner-fact text and cultural-pack eligibility, then makes **at most one** 20-second Muse call after one shared-DO unit reservation. Section and whole-article reviews remain independent calls. Failed budget reservation leaves the phase resumable without a model call; invalid model output fails the private draft closed. `GET /cultural/articles/:id` reads the checkpoint only while its source evidence remains eligible. No public article route or publication action exists. The existing `0006_longform_jobs.sql` migration must be confirmed before activation; this PR does not run it.

## Sufficiency, performance and operational bounds

The planner returns at most three research questions or explicitly stops/narrows. `assessCulturalSufficiency` can stop, request one further retrieval round, or narrow; the orchestrator caps retrieval at two rounds of at most three URLs each. No autonomous browser loop is wired into visitor requests. Retrieval is lexical-only and requires preselected allowlisted URLs. The default Editorial path pays zero extra V3 units; a preparation planner uses one unit and up to 700 completion tokens with a 12-second timeout. Candidate relationship extraction costs one more unit and at most 850 completion tokens. Private long-form uses up to 18 separate units over separate operator steps, each capped at 2500 completion tokens and 20 seconds. The existing four-unit Editor/Reviewer/Revision/Confirmation reservation remains unchanged. The existing 100-unit Standard daily/lifetime caps are shared, not extended by V3. Meta quota and price are unverified; no dollar exposure is asserted. No Production flag or source origins are configured by this PR.

## Evaluation and rollout

Automated fixtures cover exact-version binding, passage references, rights and conflict rejection, SSRF controls, lexical retrieval, planner reservation and sufficiency behavior. These are **mocked** checks, not evidence of improved Muse prose. The V2.1 baseline can be evaluated with the same approved assets and prompts only after a separate paid-test authorization. Human evaluation should score factual support/citation accuracy, connection relevance, originality/depth, hallucinations, source diversity, latency and units for: Japanese interiors, Scandinavian functionalism, jewelry craft, cultural-heritage travel, indirect cross-disciplinary topics, adversarial pages, conflicting evidence, and provider unavailability. Preserve the actual model outputs and judge blind pairs; do not infer quality from the presence of citations.

Before any activation, review an allowlist of authoritative HTTPS origins and the exact reviewed packs; verify provider quotas, shared budget headroom, current D1/R2 permissions, and a controlled fallback test. Deploy through the existing Git path with the flag still false. Configure `RESEARCH_SOURCE_ORIGINS` only for the operator research endpoint. A separate owner approval is required to enable V3 and run any paid Muse call. Rollback is `CULTURAL_INTELLIGENCE_V3_ENABLED=false`; it does not delete R2 packs or alter budget history. The deployment must read back all AI flags because source-controlled Wrangler values may replace Dashboard overrides.

## Remaining limits

This PR does not provide semantic embeddings, automatic URL discovery, a live public research loop, independent automated source-authority verification, a public citation-inspection UI, or a real paired V2.1-versus-V3 writing-quality result. The current Editorial schema carries exact cultural source IDs and optional narrative spans in `culturalClaims`; the independent Reviewer assesses semantic support. A small same-origin read-only citation contract revalidates approved source, passage rights and publication on demand; see `docs/silver-field-citations-contract.md`. The technical gate proves identity, substring mapping and permissions, not semantic truth. No live SAM capture or Meta quota has been verified in this development turn. The citation-inspection UI remains with the Silver Field owner because this PR does not alter the approved spatial frontend.
