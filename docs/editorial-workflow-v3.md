# Single AI Story Editorial Workflow V3

V3 reuses the existing Single AI Story Article Edition job, D1 catalog preparation, exact-version observations, Muse adapter, Independent Reviewer, conditional Revision/Confirmation, and Book staging. `EDITORIAL_WORKFLOW_V3_ENABLED` is optional and defaults to false. Three-story editions and V2 remain unchanged.

When enabled, a five-unit atomic reservation covers at most five Muse calls: Chief Editor Planning, Chief Editor Writing, Reviewer, Revision, Confirmation. The existing `magazine-v1` Durable Object, shared daily/lifetime ceilings, cooldown, tester windows and request leases remain authoritative. A single-story request needs five free units within the applicable hourly policy. The V3 request uses a 170-second workflow bound within the existing 180-second browser request; its D1 generation and tester concurrency leases extend to 230 seconds to avoid expiry during bounded work. Planning has a 20-second model bound; Writing retains the configured Chief bound; deterministic research has a 15-second total bound by default. `EDITORIAL_RESEARCH_TIMEOUT_MS` permits 5,000–20,000 milliseconds. A request may fail closed if provider latency exceeds these bounds. No separate research model call is made.

The internal Chief plan contains a topic, angle, argument, two or three selected exact asset IDs, and at most two precise research questions. An invalid plan fails before writing. Zero questions yields `unnecessary` and no external requests. Requested research uses official MediaWiki search and page extracts, the Met collection search/object APIs, and the V&A collections search API. Only origins explicitly listed in `RESEARCH_SOURCE_ORIGINS` are contacted, and only the three fixed API origins are supported. Search results come from those APIs; the model supplies no URLs. Redirects and responses over 64 KiB are rejected. Retrieval stops on the first directly relevant simple finding, or two distinct institutions for a complex question, with at most five candidate records examined per question and three findings total. Timeout, source failure or insufficient evidence does not block Writing.

New research sources have a distinct `retrieved_public_source` authority. Their ID fingerprints the retrieved canonical URL and passage. Only retrieved passages from the fixed allowlist that match the research question and pass the existing exact-reference structural validation are offered to the Chief Editor. The independent Reviewer must still assess actual support and treat unsupported cultural history, causation, brand influence, rights or factual claims as high-severity concerns. A URL or term match alone does not prove a cultural claim. The source text is untrusted data, never instructions. Proprietary brand facts, product specifications and rights cannot be supplied by external research. Subjective associations need no citation unless they assert a verifiable fact.

The server inserts numbered narrative markers only for cultural claims bound to a retrieved source. Optional `researchReferences` on the existing article response contains only sources cited by the final article, with source title, institution, URL and supporting passage. `aiDisclosure` contains the required one-time disclosure. The existing Book article adapter displays these in its Sources & References section; no article schema field or Book template changes are required. Old clients can ignore both optional fields. Research references expire after one hour and a removed source origin invalidates cache/job reuse. D1 catalog, permissions, asset versions and existing source records are revalidated before returning a completed job. An expired saved edition fails closed with `evidence_changed`; a fresh prompt is needed to create a new job.

Activation requires deploying with V3 off, verifying the unchanged D1/R2/DO bindings and budget history, configuring one or more of `https://en.wikipedia.org`, `https://collectionapi.metmuseum.org`, `https://api.vam.ac.uk` in `RESEARCH_SOURCE_ORIGINS`, and confirming enough shared and per-IP units remain. Then enable `EDITORIAL_WORKFLOW_V3_ENABLED=true` through the approved Cloudflare configuration process. The source-controlled Wrangler configuration is not changed here; after each Git deployment, read back effective Dashboard variables because deployment configuration can supersede manual values. Roll back immediately by setting `EDITORIAL_WORKFLOW_V3_ENABLED=false`. No D1 migration is needed.

Local tests use mocked Muse and official API responses. No live Muse or Production research acceptance is claimed. Before enabling public V3, validate official API behavior, provider quotas, the five-unit budget fit and one controlled reviewed article in the existing Reader.
