# Article Edition Chief Editor timeout

The confirmed Production response identified `chief_editor/provider_timeout` at about 20 seconds. The previous Article Edition provider fetch used `AbortSignal.timeout(20000)` for every role. A Chief response that takes longer than 20 seconds could not reach schema validation or the independent Reviewer.

`ARTICLE_CHIEF_TIMEOUT_MS` now defaults to 60000 and accepts integers from 20000 through 60000. It applies only to the Article Edition Chief Editor for both the one-story and three-story formats. Reviewer, Revision and Confirmation each retain a 20000 ms provider bound. The workflow also has a 150000 ms overall bound, including reservation and all model calls. An invalid setting fails closed before reserving units or calling Meta. Existing four-unit reservations are still charged even when a provider times out; no call is automatically retried.

The largest provider wait is 60 + 20 + 20 + 20 = 120 seconds. A PASS on the first review needs at most the Chief and Reviewer calls; a revision still requires independent Confirmation. The Article Edition browser request bound is 180 seconds, separate from the unchanged 90-second standard Editorial bound. Its overall preparation/polling bound remains 300 seconds. The D1 generation lease is 200 seconds and is renewed when generation is claimed, after the catalog preparation step. Concurrent polls see `preparing`; they cannot claim the same generating job or start another model workflow. A failed generation is stored as failed; an expired generating lease returns `generation_interrupted` rather than re-invoking the model. The 200-second lease allows 50 seconds beyond the workflow bound for D1 and response work. Existing job concurrency and inference budgets are unchanged.

Cloudflare Workers can await outbound I/O while the HTTP request remains connected; this change does not establish a guaranteed 180-second end-to-end path through every client network, Cloudflare plan, or Meta provider quota. Those external limits require a controlled live test after separate approval. A client disconnect, Worker eviction, or provider failure can still leave a job interrupted; it will not cause an automatic paid retry. If Production still fails, the existing request ID and stage-specific diagnostic identify whether it was another provider timeout, a transport failure, or validation.

No production variable change is required for the default 60-second Chief limit. To override it after approval, set `ARTICLE_CHIEF_TIMEOUT_MS` in the effective Worker environment and confirm the deployed value. A later Git/Wrangler deployment may replace Dashboard-managed variables with values from the checked-in configuration, so reconcile settings through the existing release process. Rollback is to remove the override or deploy the prior code; neither operation resets D1 jobs or inference counters. No migration is needed.
