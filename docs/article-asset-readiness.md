# Article Edition: prompt-triggered asset readiness

The previous Article Edition pool required a successful, current Meta image observation for every image before it counted toward the 15-image minimum. The D1 Reader catalog and Journey can therefore show more images than the Article Edition can use. The reported Production result, **1 of 15**, only establishes that one image passed all gates for that prompt. It does not establish how many other images lack analysis: publication, rights, Content Studio metadata, source records, exact-version identity, R2 integrity and prompt relevance also matter. This development environment has no authenticated Production inventory, so the actual per-reason Production counts remain unverified.

## Flow and contract

With `EDITORIAL_ARTICLES_ENABLED=true`, `EDITORIAL_ARTICLE_PREPARATION_ENABLED=true`, existing public Editorial and Reviewer gates enabled, and visitor consent, the existing Article Edition POST starts or resumes a deterministic D1 job. The `feat/article-asset-readiness` path uses the existing `/api/editorial` request with `editionFormat:"curio-editorial-articles-v1"`. The response remains that contract for completed editions. A prompt, mode and visitor IP are HMAC-digested for the job identity; the raw prompt and IP are not stored in the job table. The client repeats the *same* consented request automatically after a truthful HTTP 202 `preparing` response, honoring `preparation.retryAfterMs`. This is one Generate action; no user resubmission or fabricated progress percentage is required. Failure remains explicit and the standard edition remains an optional disclosed route.

The existing D1 retriever ranks up to 96 prompt-relevant versions. The pool rechecks publication, reader/display and AI permissions, required linked brand/product metadata and owner sources, exact version/SHA, private R2 object metadata and valid exact-version Meta observations. It checks at most 32 R2 objects and accepts at most 24 distinct image candidates. An observed candidate is reused without new inference. For missing evidence, the orchestrator schedules at most two exact-version Muse image analyses concurrently, using the existing D1 claim for deduplication. Failed analyses are not automatically retried. On each poll it rechecks the authoritative pool. At **15 fully eligible images**, it stops preparing and invokes the existing Chief Editor → independent Reviewer → optional targeted Revision → Confirmation once, against an immutable pool snapshot. The existing four-unit reservation, article/source validators and `curio-editorial-articles-v1` completed schema remain in force. Additional candidate analysis is not required before generation. The workflow does not start another planning agent or parallel article writers.

`article_edition_jobs` stores a bounded, resumable state and a completed approved edition. On reuse, selected images, rights, sources and exact-version observations are revalidated; revoked or changed evidence invalidates the saved result. An interrupted generation fails closed rather than automatically making another paid request. Jobs older than seven days are pruned opportunistically. Deployment requires applying `0007_article_edition_jobs.sql` through the existing migration process before enabling the new flag. The new flag defaults to `false`; without it, Article Edition retains its prior transparent insufficient-content behavior.

## Contextual evidence

`article_interpretations` stores immutable, versioned, **deterministic editorial question cues**, keyed by exact asset version and image SHA, a bounded curiosity topic, owner-source digest and observation digest. Existing cues are reused for another prompt in the same topic; different topics coexist. These cues are not Meta interpretations or verified facts. Their focus question names an owner-supplied product when available and a structured visible subject; it makes no new factual claim. A versioned `curio-article-evidence-v1` pack keeps these cues separate from owner facts and exact-version visual observations. Chief, Reviewer, Revision and Confirmation receive the same pack, and all prompts explicitly forbid treating its subjective cues as factual sources. There is no extra model call for contextual interpretation. More nuanced model-based reinterpretation would need a separately approved inference policy and is not implied by this implementation.

## Budget and limits

Each missing image analysis reserves **one** unit from the existing shared Durable Object `magazine-v1`; failed provider calls retain their reservation. Preparation has separate per-IP hourly, daily and short-window counters. A shared Durable Object lease caps **all concurrent preparation model calls across Worker requests**, not just calls within one job; the lease is released after classification and otherwise expires after 30 seconds. The exact-version D1 claim prevents concurrent duplicate model calls across jobs. Ordinary Editorial counters and cooldowns are unchanged. The existing reviewed edition may reserve four units. Shared daily/lifetime ceilings still apply. No Meta quota is assumed; account/provider limits need separate operator verification before activation. No Production flags or counters are changed by this PR.

All five preparation limits are read from the effective Worker environment on each request. Absence uses the existing defaults; malformed, inconsistent or out-of-range values fail closed before preparation. The recommended values are **not** set in `wrangler.jsonc` or Production.

| Worker variable | Default | Suggested controlled-test value | Enforced by |
| --- | ---: | ---: | --- |
| `ARTICLE_PREP_MAX_PER_HOUR` | 16 | 24 | Shared Durable Object, per IP/UTC hour |
| `ARTICLE_PREP_MAX_PER_DAY` | 24 | 48 | Shared Durable Object, per IP/UTC day |
| `ARTICLE_PREP_WINDOW_LIMIT` | 2 | 4 | Shared Durable Object, per IP/window |
| `ARTICLE_PREP_WINDOW_SECONDS` | 16 | 16 | Shared Durable Object window and client polling interval |
| `ARTICLE_PREP_CONCURRENCY` | 2 | 4 | Shared Durable Object global active leases; also bounds one job's batch |

Accepted bounds are 1–48/hour, 1–100/day, 1–4/window, 16–60 seconds and 1–4 concurrent, with day ≥ hour ≥ window ≥ concurrency. Raising these values does **not** raise the shared global daily/lifetime budget or Meta provider quota. A lease denied by the shared cap makes no reservation; a successfully reserved unit is never refunded. Changing limits while requests are in flight may leave old fixed-window counters or leases until their normal expiry; set limits before a controlled test and verify the effective values afterward.

The client allows up to 20 status requests or five minutes total for one Generate action. Each request has the existing 90-second Editorial timeout; the Worker D1 lease is 120 seconds. No automatic paid retry follows a failed analysis or interrupted edition. If budget or valid candidates run out, the route discloses the outcome and does not fabricate imagery or an article.

## Operator diagnostics and activation

The existing catalog-operator authentication protects `GET /api/operator/catalog/intelligence/articles/readiness?prompt=<encoded prompt>`. It returns aggregate counts: eligible/required, ranked/evaluated, pending/processing/failed analysis, and exclusions by relevance/window, publication, permissions, metadata, source, image integrity, observation and duplicates. It exposes no raw observations, source text, R2 keys or credentials. `relevance_or_window` includes active media beyond the top-96 prompt window and is not an exhaustive irrelevance judgment. Run it from an authenticated Media Studio session after deployment to establish the Production breakdown; this branch has not queried Production.

Activation requires the migration, the new preparation flag, and the existing Article/Public AI/Reviewer/provider/budget gates. Review provider quota and the operator budget readback first. Preserve dashboard-managed flags, secrets and D1/R2/DO bindings during Cloudflare deployment: the repository's `wrangler.jsonc` sets the new flag to `false` to prevent accidental activation. The five limit variables are deliberately absent from `wrangler.jsonc`, so they can be adjusted in the Cloudflare Dashboard without a source edit while the Worker is running. **A later Git/Wrangler deployment may replace or remove Dashboard-only variables.** Compare the active settings with the approved values after every deployment and restore them through the established deployment-safe configuration procedure before any paid test. Rollback is to set `EDITORIAL_ARTICLE_PREPARATION_ENABLED=false`; do not reset the shared Durable Object or delete saved exact-version observations. The completed Article Edition contract remains unchanged for Silver Field; only HTTP 202 preparation is new. The adapter in `src/spatial/articles.ts` handles that status inside one Generate action without modifying Exhibition, Journey or Story.
